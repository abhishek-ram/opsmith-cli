# Phase 0e: Headless mode — answer sources, the answer store and resume

**Goal:** no command ever blocks without a TTY; an unanswered question stops the run with the key and the command to resume it; and every answer is persisted the moment it is given, so a re-run never asks twice.
**Depends on:** 0c, 0d.
**Size:** L.
**Lands as:** an internal change; the phase ships as 0.5.0 when 0g lands.

## Scope

1. `HeadlessInteraction`, mode selection, and the answer sources.
2. `MissingAnswerError` (exit 3) and `PendingActionError` (exit 8), both carrying the resume command.
3. `opsmith/core/answers.py`: the answer store, non-secret and secret.
4. `opsmith/core/steps.py`: the optional ledger for non-idempotent steps.
5. `wait_for` in earnest: the DNS confirmation becomes a polled check.
6. Secret handling: build env vars out of `state.yml`, ansible extra-vars off the command line.

## Non-goals

- New commands. This part makes the existing flows headless; 0f adds the subcommands that expose them.
- Declared question trees. `env plan` is 0g. Until then a headless run discovers what it needs one answer at a time through the exit-3 loop, which is the fallback path that must work for every strategy anyway.

## Design

### Mode selection and answer sources

`HeadlessInteraction` is selected when stdin is not a TTY, `--non-interactive` is given, or `OPSMITH_NON_INTERACTIVE` is set. Answers come from, in order:

1. inline `--answer key=value`
2. `--env-file <dotenv>`, for `envvar.<KEY>` keys, secrets included
3. `--answers <file>`, a YAML mapping of key to value
4. `OPSMITH_ANSWER_<KEY>`, dots and dashes replaced by underscores, upper-cased
5. the environment's persisted answer store, so a re-run never asks twice
6. the question's own default, only under `--accept-defaults`

`select` accepts either the choice value or its label. Behaviour per primitive:

| Primitive | Headless |
|-----------|----------|
| `ask`, `select` | an answer from the sources above; the default under `--accept-defaults`; otherwise `MissingAnswerError`, exit 3, carrying key, message, choices, default and the resume command |
| `confirm` | `--yes`, or an explicit answer; keys listed as destructive never take a default; otherwise exit 3 |
| `edit` | `on_headless="accept"` returns the file unchanged; `on_headless="fail"` raises exit 4 with the path and the validate command |
| `wait_for` | polls `check` until `timeout_s` or `--wait-timeout`, then `PendingActionError`, exit 8, carrying key, `details` and the resume command |
| `notify` | appended to the result's `notices`; entries carrying a `next_steps` detail land in `next_steps` |

The resume command is the invocation that produced the error, with the answers already supplied preserved. It is the mechanical part of the driver loop: run; on exit 3 add the one missing answer and run again; on exit 8 perform the action and run again.

### The answer store

Answers persist the moment they are given, in both interactive and headless mode. Non-secret answers go to `environments/<env>/answers.yml`. A satisfied `wait_for` is recorded the same way, so a re-run does not re-poll something already true. Phase 3 syncs the store with the state file.

Secrets need care, because a secret store already exists and this part must adopt it rather than build a second one:

- The compose `.env` content is generated by the model into `DockerComposeContent.env_file_content` (`monolithic.py:56`), reconciled with the user in `_confirm_env_vars` (`monolithic.py:97-135`), passed as an ansible extra-var, and written to `/home/<user>/app/.env` on the VM with mode `0600`. It is never stored locally.
- On a later release or update it is read back by `_fetch_remote_deployment_files` (`base.py:374-417`). The VM is already the source of truth for `envvar.<KEY>` answers.

So: for the monolithic strategy the secret store *is* the env file on the VM, with a gitignored local cache used only until the VM exists. `AnswerStore` exposes one interface over both halves and routes by the `secret` flag on the question.

Two existing leaks are closed here, because this is the part that makes secret handling explicit:

- `build_env_vars` are persisted in plaintext inside `FrontendCDNState` in `state.yml` (`types.py`), including values entered through a password prompt (`monolithic.py:515`). They move into the secret store and out of the state file.
- Ansible extra-vars are passed on the command line (`ansible_provisioner.py:50-51`), so the whole `.env` body is visible in the local process table despite `no_log` on the remote task. Write them to a temporary vars file and pass `--extra-vars @file`.

### Re-runs

Every command must be safe to run again after exit 3 or exit 8. Terraform and the playbooks are idempotent already. A strategy that adds a non-idempotent step wraps it:

```python
with ctx.steps.once("vm.create"):
    ...
```

The ledger records completion in the state file and skips the block on the next run. It is a convenience for strategy authors, not part of the strategy contract — a third-party strategy that never touches it still works, as long as its steps are idempotent.

### The DNS wait

`_confirm_dns_records` (`monolithic.py:687-718`) prints the records and asks a `Confirm` that aborts the deploy on "no". It becomes `wait_for` with a resolver check per record: interactively it shows the records and re-checks on a keypress; headlessly it polls until `--wait-timeout` and then exits 8 with the outstanding records in `details`. Creating the records and running again resumes at the wait.

## Acceptance criteria

1. Running any command with stdin redirected from `/dev/null` never blocks on a prompt (phase acceptance criterion 3).
2. A run stopped by exit 3 resumes on the next invocation without re-asking anything already answered, and a run stopped by exit 8 resumes at the wait once its check passes (phase acceptance criterion 7).
3. A DNS wait whose records are never created exits 8 within the wait timeout with the records in `details`; creating them before the re-run lets the run complete (phase acceptance criterion 8).
4. A secret answer never appears in `answers.yml`, in `state.yml`, or in the argv of any subprocess.
5. `--yes` satisfies `delete.confirm` and `update.confirm_infra_changes`; `--accept-defaults` does not.
6. A fix editor (`dockerfile.edit`, `compose.edit`) headless exits 4 with the file path and the validate command; a review editor accepts the proposal and continues.
